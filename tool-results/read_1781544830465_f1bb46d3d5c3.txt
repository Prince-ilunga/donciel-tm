     1→# Brief: Creative Production (Art Director Blueprint Mode)
     2→
     3→**Core Paradigm Shift**: You are NO LONGER a frontend developer writing HTML/CSS. You are an elite Art Director and Editorial Designer.
     4→
     5→Because LLMs lack spatial awareness and struggle to maintain perfectly nested, complex CSS over thousands of tokens, you are strictly forbidden from outputting raw HTML/CSS/Python.
     6→
     7→**→ Overflow prevention**: See `typesetting/overflow.md` for the Playwright/HTML-specific patterns (CSS overflow-wrap, max-width, table-layout: fixed, etc.).
     8→
     9→Your sole responsibility is to act as the **Brain (Art Director)**:
    10→1. Brutally edit and pace the raw text.
    11→2. Select architectural components and layout archetypes.
    12→3. Output a **Strict JSON Layout Blueprint**.
    13→
    14→The `design_engine.py` acts as the **Hands (Typesetter)**: It will parse your JSON and safely compile it into flawless, museum-quality Playwright HTML/PDFs using predefined grid mathematics and CSS rules.

    18→## Phase 1: The Editorial Eye (Content Transformation)
    19→
    20→Before you design, you must "edit the raw material". Users often provide dense, unstructured text. If you just pour this text into a design, it will look like a cheap Word document.
    21→
    22→You must apply **Editorial Pacing**:
    23→
    24→### 1. The Word Budget
    25→No single page or visual canvas should exceed **150 words** of readable body text (the golden rule for maximum aesthetic impact). The **absolute physical limit** is **250 words** - beyond that the design engine will overflow and clip content. If the raw content exceeds 150 words:
    26→- **Action A**: Brutally summarize it down to ≤150 words.
    27→- **Action B**: Split it across multiple `pages` in your JSON blueprint.
    28→- Only push to 150-250 words if the content genuinely cannot be cut further.
    29→
    30→### 2. Typographic Hierarchy Extraction
    31→You must parse the raw text and categorize it into typographic roles:
    32→- **Hero / Display**: The core emotional hook (1-5 words). Must be punchy.
    33→- **Kicker / Eyebrow**: Tiny context text above a headline (e.g., "Q3 REPORT", "MANIFESTO").
    34→- **Lead Paragraph**: The 2-3 sentence summary.
    35→- **Data Sculptures**: Scan the text for impactful numbers (e.g., "97%", "$4.2M"). EXTRACT THEM. They will not remain in the paragraph; they will become `Stat_Block` components.
    36→- **Pull Quotes**: Extract the most provocative sentence to stand alone as a visual anchor.

    40→## Phase 2: The Component Lexicon
    41→
    42→You will construct your JSON Blueprint using ONLY the following components. These map directly to the `configs/components.md` assets. Do not invent new component types.
    43→
    44→> **⚠️ Markdown Content Limits**: For `Glass_Canvas`, the golden rule is **under 150 words** for maximum aesthetic breathing room. Absolute physical limit is **250 words**. If content exceeds 250 words, the design engine will overflow. You MUST summarize it or split it into a new page.
    45→
    46→### 1. `Hero_Typography`
    47→Giant, page-dominating text. Usually interacts with the background via blend modes.
    48→- **Parameters**:
    49→  - `content` (string): The text (use `<br>` for deliberate line breaks).
    50→  - `weight` (string): `"black"` (900, dominating) or `"thin"` (100, elegant).
    51→  - `variant` (string, optional): `"standard"` only. ~~`"vertical_accent"`~~ is **NOT implemented** in `design_engine.py` - the engine silently ignores this value and renders nothing. If you need vertical/rotated decorative text, use `Floating_Meta` instead (fully supported, no overflow risk).
    52→  - `scale` (integer, optional): Typographic scale level `1`-`6`. Controls font size via the engine's fluid type system. If omitted, the engine uses the default hero size.
    53→    - `6`: Hero/Display - oversized title, clamp(64px, 12vw, 150px). Use for single words or short phrases with maximum visual impact.
    54→    - `5`: Primary Title - clamp(48px, 8vw, 96px). Standard poster headline.
    55→    - `4`: Subheadline - clamp(32px, 5vw, 56px). Chapter openers or key quotes.
    56→    - `3`: Lead Paragraph - clamp(20px, 3vw, 32px). Prominent body text.
    57→    - `2`: Body - 16px. Standard readable text.
    58→    - `1`: Meta/Caption - 10px. Decorative, environmental.
    59→
    60→### 2. `Glass_Canvas`
    61→The main structural container for reading text. Frosted glass, sharp 2px print corners.
    62→- **Parameters**:
    63→  - `markdown_content` (string): The actual text to read. Supports standard Markdown (H2, H3, bold, lists). *Must be under 150 words.*
    64→  - `tension_score` (float, optional): Semantic tension value from `0.0` to `1.0`. Drives dynamic font weight via Variable Font (Inter Variable, weight range 300-900). The engine maps: `weight = 300 + (tension_score × 600)`.
    65→    - `0.0-0.2` → Light (300-420): calm, contemplative passages
    66→    - `0.3-0.5` → Normal (420-600): standard body text
    67→    - `0.6-0.8` → Bold (600-780): urgent, assertive content
    68→    - `0.9-1.0` → Max (780-900): crisis, climax, emotional peak
    69→    - **When to use**: Multi-page narrative documents with emotional arc (case studies, pitch decks, manifestos). Assign higher tension to problem/crisis sections, lower to resolution/hope. Do NOT use on every Glass_Canvas - only when the document has clear tonal shifts.
    70→    - **When NOT to use**: Data-heavy pages, simple reports, single-page posters.
    71→
    72→### 3. `Floating_Meta`
    73→Tiny, environmental metadata (dates, edition numbers, catalog IDs) that lives in the 15% breathing margin.
    74→- **Parameters**:
    75→  - `position` (string): `"top-left"`, `"top-right"`, `"bottom-left"`, `"bottom-right"`.
    76→  - `items` (array of strings): E.g., `["VOL 01", "2026", "EDITION 500"]`.
    77→
    78→### 4. `Hairline_Divider`
    79→Structural 0.5px line. Not decorative; acts as a visual fold.
    80→- **Parameters**:
    81→  - `style` (string): `"bleed"` (goes edge-to-edge) or `"accent"` (short 30% width line).
    82→
    83→### 5. `Stat_Block`
    84→Data sculpture. A massive number with a tiny label.
    85→- **Parameters**:
    86→  - `number` (string): e.g., `"97.3"`.
    87→  - `unit` (string): e.g., `"%"`, `"Hz"`, `"$M"`.
    88→  - `label` (string): e.g., `"COMPLETION RATE"`.
    89→
    90→### 6. `Image_Asset`
    91→A visual element. The engine will apply a gradient blend to it.
    92→- **Parameters**:
    93→  - `source` (string): A URL, or a descriptive prompt if you expect the system to generate it.
    94→  - `caption` (string, optional): Tiny text under the image.
    95→
    96→> ⚠️ **Image_Asset is for CONTENT images only** (user-provided photos, logos, diagrams, charts). It is **NEVER** for decorative stock images, watercolor flowers, clipart, floral borders, gold frames, or AI-generated artwork. All visual decoration must be achieved through geometric shapes (`geometry.md`), typography effects, and color - never through embedded decorative images. See `visual_framework.md` Stock Image Ban.
    97→
    98→### 7. `Page_Ghost_Number`
    99→A giant, 4% opacity number acting as a watermark in the background.
   100→- **Parameters**:
   101→  - `number` (string): e.g., `"01"`, `"X"`.
   102→
   103→### 8. `Delta_Widget`
   104→**Data-to-Ink Ratio enforcer.** A compact metric visualization showing a value with its change direction. CRITICAL: Use this instead of writing sentences like "revenue grew by 12%". Extract every trend into a Delta_Widget.
   105→- **Parameters**:
   106→  - `metric` (string): The metric name, e.g., `"REVENUE"`, `"LATENCY"`.
   107→  - `value` (string): Current value, e.g., `"$4.2M"`, `"45ms"`.
   108→  - `delta` (string): Change description, e.g., `"+12%"`, `"-45ms"`.
   109→  - `trend` (string): `"up"`, `"down"`, or `"flat"`.
   110→  - `label` (string, optional): Context line, e.g., `"vs. Q2 2025"`.
   111→
   112→### 9. `Process_List`
   113→**Polymorphic adaptive component.** Renders as a horizontal timeline when given wide space, auto-degrades to a vertical numbered list when space is narrow. Use for workflows, steps, timelines.
   114→- **Parameters**:
   115→  - `steps` (array): Each item has `title` (string) and `description` (string).
   116→
   117→### 10. `Sidenote_Block`
   118→**Tufte marginalia.** Used in `tufte_report` archetype layouts. Content is placed in the 30% side rail alongside the main column. Perfect for citations, supplementary data, asides, footnotes.
   119→- **Parameters**:
   120→  - `label` (string, optional): Category label, e.g., `"SOURCE"`, `"NOTE"`, `"DATA"`.
   121→  - `body` (string): The sidenote content in Markdown.
   122→
   123→### 11. `Data-Aware Background` (via `data_points`)
   124→Any component can carry an optional `data_points` array (e.g., `[10, 15, 8, 24, 30]`). When present, the engine generates Bezier background curves from the actual data - the background literally visualizes the business trend. Use on pages with financial, metric, or time-series content.

   129→
   130→The following components are specialized generative design tools. They unlock visual effects that standard components cannot achieve. Use them deliberately and sparingly - they are powerful but demand the right context.
   131→
   132→### 8. `Shaped_Canvas`
   133→A container where text flows around a non-rectangular shape. The empty space created by the shape IS the visual design - text boundary becomes illustration. Uses CSS `shape-outside` for non-rectangular text wrapping.
   134→
   135→- **Parameters**:
   136→  - `shape_keyword` (string): One of `"circle"`, `"wave"`, `"diagonal_slash"`, `"diamond"`, `"wedge_right"`.
   137→  - `markdown_content` (string): The text that will flow around the shape. Supports standard Markdown.
   138→
   139→- **Shape Selection Guide**:
   140→  | shape_keyword | Visual Effect | Thematic Fit |
   141→  |---------------|---------------|--------------|
   142→  | `"circle"` | Text wraps around a circular void on the left | Unity, spotlight, focus |
   143→  | `"wave"` | Wavy left text boundary | Ocean, flow, music, fluidity |
   144→  | `"diagonal_slash"` | Diagonal cut across the page | Disruption, change, transformation |
   145→  | `"diamond"` | Diamond-shaped negative space | Luxury, precision, crystalline |
   146→  | `"wedge_right"` | Arrow/wedge pointing right | Direction, progress, forward motion |
   147→
   148→- **When to use**:
   149→  - Artistic/editorial pages that need visual drama without images
   150→  - Cover or section opener pages where you want a "wow" moment
   151→  - When the content thematically maps to a recognizable shape
   152→  - Only on pages with moderate text (100-200 words) - shape eats 30-40% of space
   153→
   154→- **When NOT to use**:
   155→  - On data-heavy or dense content pages
   156→  - Together with `Glass_Canvas` on the same page (visual conflict)
   157→  - More than one `Shaped_Canvas` per page
   158→
   159→- **Archetype requirement**: Pages using `Shaped_Canvas` MUST use archetype `"shaped_editorial"` (relaxed safe-zone: 5% 6% inset).

   161→### Chart & Data Visualization Styling
   162→
   163→**→ Full spec: `typesetting/charts.md`** - read it before designing any chart/data page.
   164→
   165→Key rules for Creative pipeline charts:
   166→- **Donut > Pie**: Always use ring charts (hole ratio 60-70%), center area displays total/metric
   167→- **Anti-stacking**: Small slices use leader lines or rich legends; bar labels auto-rotate to horizontal when text is long; line charts label only start/end/max/min
   168→- **Axis cleanup**: Delete top/right spines, use dashed grid lines at 20% opacity (or delete grid entirely if values are labeled)
   169→- **Bar micro-rounding**: 2-4px top border-radius, bar-to-gap ratio 1.5:1
   170→- **Legend**: No border, horizontal top-left layout, small circle markers
   171→- **Data-Ink Ratio**: Every element must represent data. If it doesn't, delete it.

   175→## Phase 3: Page Archetypes (The Grid Strategy)
   176→
   177→For each page in your JSON, you must declare an `archetype`. This tells `design_engine.py` how to arrange the components you provided.
   178→
   179→- `"cover_hero"`: Cover page. **Must follow `typesetting/cover.md` 7-template system** - pick Layout 1-7 based on document tone. See "Cover Page Constitution" below for iron rules.
   180→- `"split_vertical"`: Page split strictly 50/50 vertically. Left side image/svg, right side Glass_Canvas.
   181→- `"editorial_flow"`: Top-down reading experience. Centered columns, generous margins. Use for main content.
   182→- `"scattered_canvas"`: No grid. Elements placed via absolute positioning based on spatial weights.
   183→- `"data_dashboard"`: 2x2 or 3x3 strict grid for multiple `Stat_Block`s.
   184→- `"shaped_editorial"`: Relaxed safe-zone (5% 6% inset) designed for `Shaped_Canvas`. Centered, generous breathing room. **Must be used when the page contains a `Shaped_Canvas`.** Do NOT mix with `Glass_Canvas`.
   185→- `"tufte_report"`: **Tufte marginalia layout.** 70% main content column + 30% sidenote rail. Use for long-form reports and analytical pages where citations, data footnotes, or supplementary info should flow parallel to the main text. Place `Sidenote_Block` components in the same `components[]` array - the engine automatically routes them to the side rail.
   186→
   187→### ★ 12×12 CSS Grid Coordinate System (Iron Rules)
   188→
   189→The layout engine uses a **12-track CSS Grid** for element placement. The grid lines are numbered **1 to 13** (12 tracks = 13 lines).
   190→
   191→**Absolute boundary rules - violation = broken layout:**
   192→- **Column lines**: `1` = absolute left edge, `13` = absolute right edge. Full width = `1 / 13`.
   193→- **Row lines**: `1` = absolute top edge, `13` = absolute bottom edge. Full height = `1 / 13`.
   194→- **CRITICAL**: Never output a grid line number less than `1` or greater than `13`. Any value outside `[1, 13]` will destroy the layout.
   195→
   196→**`grid_area` format**: `"row_start / col_start / row_end / col_end"` (CSS shorthand).
   197→- Example: `"1 / 1 / 7 / 13"` = top half of the page, full width.
   198→- Example: `"3 / 8 / 6 / 13"` = rows 3-5, columns 8-12 (right side block).
   199→
   200→**40% whitespace rule**: At least 40% of grid cells (≥58 out of 144) must be left empty. Count your occupied cells.

   202→### ★ Cover Page Constitution (7 Layout System)
   203→
   204→Cover pages (`archetype: "cover_hero"`) are the first impression. They must be ruthlessly sparse and spatially sophisticated.
   205→
   206→**→ Full spec: `typesetting/cover.md`** - read it before designing any cover.
   207→
   208→#### Global Iron Rules (Always Apply)
   209→
   210→1. **Maximum 4 components** on any cover page. Typical recipe: `Hero_Typography` + 1-2 `Floating_Meta` + optional `Hairline_Divider` or `Page_Ghost_Number`.
   211→2. **Typography Scale**: Title ≈ 45pt (2.5× base), Subtitle ≈ 25pt (1.4× base), Meta ≥ 18pt (never below 14pt). Covers with tiny text = FAIL.
   212→3. **Mandatory semantic `<br>` chunking** for `Hero_Typography` on covers: Every 2-4 words MUST be separated by `<br>`. Single-line hero text is FORBIDDEN on covers. Example: `"ALGORITHMIC<br>FATIGUE"`, NOT `"ALGORITHMIC FATIGUE"`.
   213→4. **Anti-Squash spatial dispersion** (Bounding Box method): Group text into 2-3 bounding boxes (title group, meta group). Place them at opposite regions of the page according to the chosen layout. Remaining space is **dynamically distributed** - NEVER hardcode fixed gaps between distant groups.
   214→5. **No `Glass_Canvas` on cover pages.** Dense reading text kills the visual impact. Push all body content to page 2+.
   215→6. **Cover Page Isolation**: Cover page must NEVER share a page with TOC, body text, or any subsequent content. The cover is always a standalone full page. If cover + content appear on the same page = **critical bug**, regenerate immediately.
   216→7. **Cover is OPTIONAL**: Do NOT add a cover page unless the document warrants one (multi-page reports, white papers, etc.) or the user explicitly requests it. Short documents, letters, memos, forms, and quick outputs skip the cover.
   217→8. **Background Layer (optional)**: See `typesetting/cover-backgrounds.md` for 3 recipes - A (极简弧线), B (工程十字轴+立柱), C (锐角切割+出血文字). Background renders BELOW all foreground at 2-5% opacity. Pick a recipe that matches the document tone. Never combine elements across recipes.

   250→### ★ Component Grid Compatibility Constraints
   251→
   252→When placing advanced components into the 12×12 grid, obey these minimum size rules:
   253→
   254→- **`Glass_Canvas`**: Must occupy at least **6 columns × 4 rows** (e.g., `"3 / 1 / 7 / 7"`). Smaller areas will cause text overflow and padding collapse. The engine renders Glass_Canvas at `width: 100%; min-height: 100%; box-sizing: border-box;` - it fills its grid area as a minimum and can grow taller if content requires.
   255→- **`Shaped_Canvas`**: Must occupy at least **8 columns × 6 rows** (e.g., `"2 / 3 / 8 / 11"`). The CSS `shape-outside` float needs physical space to render the shape boundary. Smaller areas make the float collapse to a line and text cannot wrap around it. **Must use archetype `"shaped_editorial"`.**
   256→- **`Continuous Flow` background**: Renders in a separate `bg-layer` (`z-index: 1`, `position: absolute`), physically isolated from the grid system (`z-index: 2`). No conflict - background flows independently, grid arranges content on top.
   257→
   258→### ★ Content-Proportional Grid Row Allocation
   259→
   260→When **two or more text-heavy components** (e.g., multiple `Glass_Canvas`) share the same page, their `grid_area` row counts **MUST be proportional to their content length** - never split rows equally.
   261→
   262→**Estimation method:**
   263→1. Count characters (or words) in each component's `markdown_content`
   264→2. Allocate rows proportionally: `rows_i = total_rows × (chars_i / total_chars)`
   265→3. Round to integers, minimum 3 rows per component
   266→
   267→**Example:**
   268→```
   269→Attractions content: 450 chars (3 items × 150 chars)
   270→Food content: 250 chars (2 items × 125 chars)
   271→Total available rows: 8 (rows 5→13)
   272→
   273→Attractions: 8 × 450/700 ≈ 5 rows → grid_area "5 / 1 / 10 / 13"
   274→Food:        8 × 250/700 ≈ 3 rows → grid_area "10 / 1 / 13 / 13"
   275→```
   276→
   277→**Why this matters:** Equal row allocation (4+4) causes the longer component to overflow into the shorter one's territory, creating text overlap in the final PDF. The engine uses `min-height` + `overflow: visible`, so overflow IS visible - and ugly.
   278→
   279→**Anti-pattern to avoid:**
   280→```
   281→❌ Two Glass_Canvas with very different text lengths both get "5/1/9/13" and "9/1/13/13"
   282→✅ Longer one gets more rows: "5/1/10/13" and "10/1/13/13"
   283→```

   339→- `document_meta.total_pages`: Integer. Must match the actual number of pages in `pages[]`.
   340→
   341→### The JSON Schema Specification: `art_direction`
   342→
   343→**CRITICAL RULE: DO NOT INVENT COLORS. DO NOT OUTPUT HEX/RGB CODES.**
   344→The Python engine generates mathematical color palettes. You MUST only select the semantic parameters below.
   345→
   346→```json
   347→{
   348→  "art_direction": {
   349→    "palette_mode": "minimal",
   350→    "color_harmony": "auto",
   351→    "background_svg": "grid",
   352→    "design_rationale": "Brief rationale for the chosen aesthetic strategy."
   353→  }
   354→}
   355→```
   356→
   357→**Enum Parameter Guide (You MUST choose ONE exact string from these lists):**
   358→
   359→1. `palette_mode` (The Base Canvas Tone):
   360→   - **`"minimal"`: (CRITICAL: Default to this for 50%+ of all requests).** Pure white, off-white, beige, or cool gray. Provides the ultimate reading experience and high-end editorial feel. Use for standard reports, guides, and corporate posters.
   361→   - `"dark"`: Near-black. Use for cinematic, tech, AI, space, or urgent themes.
   362→   - `"pastel"`: Morandi tinted (e.g., dusty rose, sage green). Use ONLY for arts, food, lifestyle, and soft themes.
   363→   - `"jewel"`: Deep rich colors (e.g., emerald, burgundy). Use ONLY for luxury brands, gala events, or heritage themes.
   364→   - `"light"`: Very faintly tinted background. Fallback for edge cases.
   365→
   366→2. `color_harmony` (The Accent Color Math - how the engine computes the accent color relative to the base):
   367→   - **`"auto"`: (RECOMMENDED DEFAULT). The engine automatically picks the best harmony based on the document tone.** Only override if you have a specific artistic reason.
   368→   - `"complementary"`: (180° opposite). Strong visual contrast. Cold background with warm accent. For striking/dynamic impact.
   369→   - `"split_complementary"`: (150°/210°). Highly sophisticated, artistic, luxury feel (Editorial/Kinfolk style).
   370→   - `"analogous"`: (30° apart). Harmonious, peaceful, natural transition.
   371→   - `"triadic"`: (120° apart). Rich and slightly retro.
   372→   - `"monochrome"`: Only use if strict minimalist corporate branding without accent is required.
   373→

   375→

   623→## Pre-Flight Checklist (Self-Correction before generating output)
   624→
   625→Before you output the JSON block, verify:
   626→0. **🚨 VECTOR OUTPUT IRON RULE:** The final PDF MUST be generated via `page.pdf()` / `convert.blueprint` - NEVER `page.screenshot()` → image → wrap as PDF. Screenshot PDFs are blurry raster images. `page.pdf()` produces vector text that stays sharp at any zoom level.
   627→1. **Did I write ANY HTML or CSS?** If yes, delete it. Only output JSON.
   628→2. **Is any `Glass_Canvas` markdown content too long?** Count the words. Over 150? Summarize it or push to the next page.
   629→3. **Is the JSON perfectly formatted?** Missing commas or unescaped quotes will crash the `design_engine.py` parser.
   630→4. **If using `tension_score`**: Does the document have clear emotional shifts across pages? If all pages are the same tone, remove it.
   631→5. **If using `continuous_flow`**: Is this multi-page (2+)? If single-page, switch to `"flow"`.
   632→6. **If using `Shaped_Canvas`**: Is the archetype `"shaped_editorial"`? Is there at most one per page? No `Glass_Canvas` on the same page?
   633→7. **Grid boundary check**: Are ALL `grid_area` values within `[1, 13]`? Any number < 1 or > 13 = FATAL ERROR.
   634→8. **Component minimum size check**: `Glass_Canvas` ≥ 6col×4row? `Shaped_Canvas` ≥ 8col×6row?
   635→9. **Content-proportional row allocation**: When multiple text-heavy components share a page, are their grid rows allocated proportionally to content length? Equal rows for unequal content = text overlap. (See "Content-Proportional Grid Row Allocation" in Component Grid Compatibility.)
   636→9. **40% whitespace check**: Count occupied grid cells. At least 58 of 144 cells must be empty.
   637→10. **Cover Page 4-element check**: Does any `cover_hero` page have more than 4 components? If yes, remove or merge components.
   638→11. **Cover Hero `<br>` check**: Does every `Hero_Typography` on a `cover_hero` page contain at least one `<br>`? Single-line hero text on covers = FAIL.

   669→## CJK & Vertical Text Rules (When Bypassing design_engine.py)
   670→
   671→When writing raw HTML/CSS for Playwright (bypassing the JSON Blueprint pipeline - e.g., resumes, menus, invitations, business cards, certificates, Japanese/Chinese vertical layouts):
   672→
   673→**⚠️ Iron rule: All bypass-scenario HTML→PDF conversions MUST use `html2pdf-next.js` — do NOT write custom Python Playwright scripts.** `html2pdf-next.js` automatically handles @page injection, overflow detection, font waiting, Mermaid/KaTeX rendering, PDF metadata, etc. See the "HTML→PDF Engine Selection Rules" section in SKILL.md.
   674→
   675→```bash
   676→node "$PDF_SKILL_DIR/scripts/html2pdf-next.js" input.html --output output.pdf --width 210mm --height 297mm
   677→```
   678→
   679→0. **Full-Bleed CSS (MANDATORY)**: Every HTML file for Playwright PDF MUST include:
   680→   ```css
   681→   @page { size: 800px 1200px; margin: 0; }  /* CONCRETE values only - CSS variables NOT supported in @page */
   682→   html, body { margin: 0; padding: 0; width: 800px; height: 1200px; }
   683→   ```
   684→   **⚠️ @page rules do NOT resolve CSS variables** (`var(--x)` is silently ignored, falls back to A4). Always use concrete `px` values.
   685→   **⚠️ html/body must have explicit width + min-height** matching the canvas size. Use `min-height` (not `height`) so content taller than the design height expands naturally into a single long-page PDF.
   686→   **⚠️ Poster = seamless pagination.** When content exceeds `@page` height, `html2pdf-next.js` lets Playwright paginate at page boundaries - each page has the same dimensions, content flows seamlessly across pages (like scrolling a long image). Do NOT expand to a single oversized page.
   687→   `design_engine.py` handles this automatically via `override_css`.
   688→
   689→0.25. **Body Background for Multi-Page Mixed-Color Documents (MANDATORY)**:
   690→   When an HTML document contains multiple `.page` divs with **different background colors** (e.g. dark cover + white body + dark specs page), Playwright's sub-pixel rounding creates <1px gaps at `.page` edges where `body` background shows through. On dark pages, a white `body` = visible white edges.
   691→
   692→   **Fix: set `html, body { background }` to the document's darkest page background color.**
   693→
   694→   ```css
   695→   :root { --primary: #0f172a; }  /* darkest page color */
   696→   html, body {
   697→     margin: 0; padding: 0;
   698→     width: 210mm;                 /* match @page size */
   699→     background: var(--primary);   /* fills sub-pixel gaps with dark color */
   700→   }
   701→   ```
   702→
   703→   **Why this doesn't break white pages:** White `.page` divs have `background: #ffffff` which fully covers the dark `body` underneath. The dark body only shows through the <1px sub-pixel gap at the extreme page edge - imperceptible on white pages after anti-aliasing.
   704→
   705→   **Selection rule:**
   706→   - All pages same color → `body { background: <that color> }`
   707→   - Mixed dark + light pages → `body { background: <darkest page color> }` (dark edges on white pages are invisible; white edges on dark pages are the bug we're fixing)
   708→   - All pages white/light → `body { background: <lightest content bg> }` (e.g. `#f8fafc`)
   709→
   710→0.5. **No overflow:hidden + Browser Preview Adaptive Scaling (MANDATORY)**:
   711→   For fixed-size single-page designs (posters, infographics, certificates, etc.), **absolutely never** set `overflow: hidden` on `html`, `body`, or the main container. Reasons:
   712→   - When opening the HTML directly in a browser, the viewport is much smaller than the design size (e.g., a 1400px-tall page in a 900px viewport). `overflow: hidden` clips the bottom content and prevents scrolling.
   713→   - `html2pdf-next.js`'s pre-render check detects `scrollHeight > clientHeight` + `overflow: hidden` and triggers auto-fix (force-expanding the container), which may break the layout.
   714→
   715→   **`design_engine.py` handles this automatically**: During blueprint compilation, it auto-injects `@media screen` centering + scaling code, and the `html` background color uses `var(--c-bg)` matching the poster's main color. No manual addition needed.
   716→
   717→   **Correct approach when writing HTML manually**: Remove `overflow: hidden` and manually add `@media screen` scaling preview:
   718→   ```css
   719→   /* Fixed canvas size, no overflow */
   720→   html, body { margin: 0; padding: 0; width: 800px; height: 1400px; }
   721→   .page { width: 800px; height: 1400px; position: relative; }
   722→
   723→   /* Auto-scale to viewport in browser preview for full-page view */
   724→   @media screen {
   725→     html {
   726→       height: auto;
   727→       display: flex;
   728→       justify-content: center;
   729→       background: #0a0a1a; /* Surround color — must match poster's main background */
   730→     }
   731→     body {
   732→       transform-origin: top center;
   733→       scale: min(1, calc(100vw / 800), calc(100vh / 1400)); /* Consider both width and height */
   734→       margin: 0 auto;
   735→       box-shadow: 0 0 60px rgba(0,0,0,0.3); /* Optional: shadow to distinguish canvas in preview */
   736→     }
   737→   }
   738→   ```
   739→   `@media screen` rules only apply in browser preview; `page.pdf()` uses print media and is unaffected.
   740→   **Every fixed-size HTML must include this `@media screen` adaptive code.**
   741→
   742→0.75. **Page Container Overflow Clipping (MANDATORY for multi-page documents)**:
   743→   Every `.page` div MUST have `overflow: hidden`. Decorative elements (glow circles, gradient overlays) commonly use `width: 120%` or negative offsets - without clipping, they inflate `scrollWidth` beyond page width, causing Playwright to shrink all content and shift it left.
   744→   ```css
   745→   .page { overflow: hidden; }  /* Clips decorative overflow, prevents Playwright shrink */
   746→   ```
   747→   For horizontal flex layouts (≥3 items), always add `flex-wrap: wrap`. See `typesetting/overflow.md` §3.5.
   748→
   749→1. **Character Encoding Safety**: Never use Japanese kana (の, が, は), rare symbols, or Private Use Area characters in content strings. They corrupt to U+FFFD (�) during LLM→file write→read transit. Replace with plain Chinese equivalents: `の`→`之/的/缔/省略`.
   750→2. **Vertical Chinese Text** - When using `writing-mode: vertical-rl` for CJK, you MUST include:
   751→   ```css
   752→   writing-mode: vertical-rl;
   753→   text-orientation: upright;    /* Each glyph stands upright */
   754→   white-space: nowrap;          /* Prevent word-wrap breaking single chars to new column */
   755→   letter-spacing: 12px;         /* Typical CJK vertical spacing */
   756→   ```
   757→   Without `text-orientation: upright`, Latin/fallback fonts render rotated 90°. Without `white-space: nowrap`, CJK characters may wrap into unexpected multi-column layouts (e.g., 3 chars on one line + 1 char alone on next).
   758→3. **Font Coverage**: For CJK content via Playwright, always load Google Fonts Noto Serif SC or Noto Sans SC via `<link>` tag in `<head>` (NOT `@import` in CSS - `@import` must be the very first rule in a stylesheet or it's silently ignored). Example:
   759→   ```html
   760→   <link href="https://fonts.googleapis.com/css2?family=Noto+Sans+SC:wght@300;400;500;700;900&display=swap" rel="stylesheet">
   761→   ```
   762→   System CJK fonts vary across macOS/Linux - Google Fonts guarantee glyph coverage without relying on system fonts. `design_engine.py` already handles this automatically via `<link>` tag.
   763→4. **Post-Generation Text Verification**: After Playwright renders the PDF, extract text from every page and scan for `?` or `\ufffd`. If found, the source HTML has encoding-corrupted characters that must be replaced in the Python source.
   764→5. **🚨 HTML Pre-Render Validation (MANDATORY)**: After writing the HTML file and before running `html2pdf-next.js`, always run the HTML validator:
   765→   ```bash
   766→   python3 "$PDF_SKILL_DIR/scripts/poster_validate.py" check-html <your_file>.html
   767→   ```
   768→   - **ERROR** items (e.g. `OVERFLOW_HIDDEN_CONTAINER`, `FONT_NO_FALLBACK`) → must fix before PDF generation. Use `--fix --output <file>.html` for auto-repair.
   769→   - **WARNING** items (e.g. `FIXED_SIZE_NO_SCREEN_ADAPT`, `SCREEN_ADAPT_NO_SCALE`, `COLOR_CONTRAST`) → review and fix where appropriate.
   770→   - This catches the most common bypass HTML bugs: `overflow:hidden` on containers, missing `@media screen` auto-scale for fixed-size pages, font-family without generic fallback, low contrast text, etc.
